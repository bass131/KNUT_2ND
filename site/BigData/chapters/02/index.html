01

같은 실습 환경이 필요한 이유

코드가 같아도 Java나 Python 버전이 다르면 결과가 달라지거나 실행에 실패할 수 있습니다. Docker는 프로그램과 필요한 실행 환경을 묶어 이런 차이를 줄입니다.

먼저 알아둘 세 용어

  • 프로세스: 지금 실행 중인 프로그램입니다.
  • 서버: 다른 프로그램의 요청에 응답하는 프로그램 또는 그 컴퓨터입니다.
  • 클러스터: 여러 실행 주체가 협력하는 구성입니다. 이번 실습에서는 한 PC 안에 여러 프로세스를 띄워 구성합니다.
학습용 비유 · 하나의 작업대, 나뉜 작업 공간

한 작업대의 상자마다 도구와 재료를 구분해 담듯, 컨테이너도 실행 환경을 구분합니다. 이미지는 각 환경을 만드는 공통 틀입니다.

03

Compose로 컨테이너 설정 읽기

Compose 파일은 “무엇을 어떤 설정으로 실행할지” 선언합니다. 먼저 공통 설정을 한 번 쓰고, 서비스마다 필요한 역할을 덧붙입니다.

학습용 비유 · 공통 준비물과 개인 역할표

팀의 공통 준비물을 한 번 적고 개인 역할을 덧붙이는 방식입니다. YAML의 공통 묶음도 설정을 재사용하며, 별도 컨테이너를 만들지는 않습니다.

공통 설정: 한 번 쓰고 재사용

YAML은 들여쓰기로 포함 관계를 표현하는 설정 형식입니다. 아래는 compose.yaml 전체 원본에서 발췌한 공통 설정입니다.

name: bigdata-week02

x-spark: &spark
  image: spark:4.1.3-scala2.13-java21-python3-ubuntu
  environment:
    PYSPARK_PYTHON: python3
  init: true
  stop_grace_period: 30s

services:
공통 설정을 한 줄씩 해석하기
설정뜻
nameCompose 프로젝트 이름입니다. 이 구성의 컨테이너와 네트워크를 묶어 구분합니다.
x-spark: &sparkx-는 재사용용 확장 필드, &spark는 설정 묶음에 붙인 anchor(참조 이름)입니다.
<<: *spark각 서비스에서 공통 설정을 가져와 합칩니다. *spark는 그 이름을 다시 가리키고 <<는 합치기를 뜻합니다.
PYSPARK_PYTHON: python3Python으로 Spark를 사용하는 PySpark가 컨테이너 내부의 python3를 쓰도록 합니다.
init: true작은 관리 프로세스를 맨 먼저 실행해 종료 신호 전달과 자식 프로세스 종료 정리를 돕습니다.
stop_grace_period: 30s중지 시 정상 종료를 위해 최대 30초를 기다립니다.

Master: 상태 확인을 통과하면 다음 서비스 시작

  spark-master:
    <<: *spark
    hostname: spark-master
    entrypoint: ["/opt/spark/bin/spark-class"]
    command: ["org.apache.spark.deploy.master.Master", "--host", "spark-master", "--port", "7077", "--webui-port", "8080"]
    ports:
      - "127.0.0.1:8080:8080"
    healthcheck:
      test: ["CMD", "python3", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8080', timeout=3)"]
      interval: 5s
      timeout: 5s
      retries: 20
      start_period: 20s
  • entrypoint: 처음 실행할 프로그램입니다.
  • command: 그 프로그램에 전달할 실행 내용입니다. 여기서는 Spark의 Master 프로그램을 실행합니다.
  • hostname: 컨테이너 내부 호스트 이름입니다.
  • healthcheck: Engine이 Master 안에서 HTTP UI 응답을 주기적으로 확인하도록 합니다. 상태는 starting → healthy 또는 unhealthy로 표시됩니다.
healthcheck 시간 옵션 더 보기
  • interval: 검사 간격입니다.
  • timeout: 한 검사에 허용하는 시간입니다.
  • retries: 연속 실패 판단 기준입니다.
  • start_period: 초기 준비 시간을 고려하는 설정입니다.

healthy는 이 UI 검사에 통과했다는 뜻이며 계산 성공을 증명하지는 않습니다.

Worker: 제공할 CPU와 메모리 알리기

  spark-worker-1:
    <<: *spark
    hostname: spark-worker-1
    entrypoint: ["/opt/spark/bin/spark-class"]
    command: ["org.apache.spark.deploy.worker.Worker", "--host", "spark-worker-1", "--cores", "1", "--memory", "1g", "--webui-port", "8081", "--work-dir", "/tmp/spark-work", "spark://spark-master:7077"]
    ports:
      - "127.0.0.1:8081:8081"
    depends_on:
      spark-master:
        condition: service_healthy

Worker 하나가 Master에 알리는 자원은 1 core, 1 GiB입니다.

  • core: 계산을 수행할 CPU 자원 단위입니다.
  • GiB: 메모리 용량 단위입니다. 여기서 1 GiB는 1024 MiB입니다.
  • --work-dir: 작업 파일과 로그 경로입니다.

Worker 2는 같은 역할이며 이름은 spark-worker-2, 호스트 UI 포트는 8082입니다.

설정의 적용 범위
  • --memory 1g: Spark에 제공할 자원 선언입니다. 컨테이너 전체의 메모리 상한은 아니며, 실제 자원은 PC·Docker 설정에도 좌우됩니다.
  • depends_on: service_healthy: 시작 조건입니다. 이후 Master 장애를 자동 복구하지는 않습니다.

Client: 코드를 읽을 수 있게 연결하고 대기

  spark-client:
    <<: *spark
    hostname: spark-client
    entrypoint: ["/bin/bash", "-lc"]
    command: ["exec sleep infinity"]
    ports:
      - "127.0.0.1:4040:4040"
    volumes:
      - ./apps:/opt/spark/apps:ro
    depends_on:
      spark-master:
        condition: service_healthy
Bash의 시작 옵션 더 보기

shell은 명령을 해석하는 프로그램입니다. 여기서는 Bash를 사용합니다.

  • -l: login 모드의 시작 설정을 사용합니다.
  • -c: 뒤 문자열을 명령으로 실행합니다.

exec sleep infinity는 shell을 계속 대기하는 프로그램으로 바꿔 Client가 종료되지 않게 합니다. 이 시점에는 Driver가 없습니다.

실습 폴더 연결: bind mount

bind mount는 호스트 폴더를 컨테이너에서 보이게 연결하는 방식입니다. ./apps:/opt/spark/apps:ro의 세 부분을 읽어 보세요.

  • ./apps: 호스트에 있는 실습 코드 폴더입니다.
  • /opt/spark/apps: Client 안에서 그 폴더를 읽을 경로입니다.
  • ro: read-only, 즉 컨테이너에서 읽기 전용이라는 뜻입니다.

파일을 따로 복사하지 않아도 Client에서 Windows의 실습 코드를 읽어 실행할 수 있습니다.

04

Spark 구성요소의 역할과 실행 순서

Spark는 데이터를 나누어 여러 실행 주체가 처리하게 하는 엔진입니다. 이번에는 Spark 자체의 클러스터 관리 방식인 Standalone을 사용합니다.

학습용 비유 · 팀 실험의 자리와 작업

Master는 자리를 배정하고, Worker는 계산 담당자를 준비하며, Driver는 실험 순서를 조정하는 역할에 비유할 수 있습니다. 실제로는 프로세스끼리 통신합니다.

비슷해 보이지만 다른 Spark 역할
역할언제, 어디에서하는 일
MasterMaster 컨테이너에서 계속 실행Worker와 가용 자원을 관리하고 Executor를 어느 Worker에서 시작할지 배정합니다.
Worker두 Worker 컨테이너에서 계속 실행Master에 등록하고, 지시에 따라 자기 쪽에서 Executor를 시작·관리합니다.
ClientClient 컨테이너는 처음에는 대기실습 코드를 제출하는 실행 장소입니다.
Driver앱 제출 후 Client에서 실행앱의 진행을 조정하고 Executor에 Task를 배정하며 결과를 확인합니다.
Executor앱 제출 후 Worker 쪽에서 실행실제 데이터 처리 Task를 실행하는 애플리케이션별 프로세스입니다.

준비 → 제출 → 계산

  1. 준비: Compose가 네 컨테이너 실행을 요청하고 Worker가 Master에 등록합니다. 별도 SSH 로그인이나 키 복사는 필요 없습니다.
  2. 제출: Client에서 spark-submit을 실행하면 Driver가 앱을 등록하고 자원을 요청합니다. Master는 Worker에 Executor 시작을 지시합니다.
  3. 계산: Executor가 Driver에 연결합니다. Driver와 Executor가 Task 지시·상태·결과를 직접 주고받습니다. Master가 모든 계산 메시지를 중계하지 않습니다.
  • Task: Executor가 수행하는 작은 작업 단위입니다.
  • Worker와 Executor: Worker는 Executor를 관리하고, Executor가 Task를 실행합니다.
  • 이번 실습의 자원: 네 컨테이너 모두 한 PC의 자원을 사용합니다.

앱을 제출하기 전, Worker 2개가 ALIVE라면?

접속 위치에 맞는 주소와 포트 고르기

프로그램에 연결할 때는 주소와 포트로 목적지를 지정합니다.

  • 포트: 컴퓨터나 컨테이너 안의 통신 창구를 구분하는 번호입니다.
  • 호스트: 여기서는 Docker를 실행하는 Windows PC입니다.
학습용 비유 · 건물 주소와 창구 번호

IP는 건물 주소, 포트는 창구 번호, DNS는 이름으로 주소를 찾는 안내부에 비유할 수 있습니다. 주소를 찾은 뒤에는 프로그램끼리 직접 통신합니다.

실습의 접속 경로
출발 위치·목적쓸 주소도착 위치
Windows 브라우저 → Master UIlocalhost:8080Master 내부 8080
Windows 브라우저 → Worker 1 UIlocalhost:8081Worker 1 내부 8081
Windows 브라우저 → Worker 2 UIlocalhost:8082Worker 2 내부 8081
Windows 브라우저 → Driver UIlocalhost:4040앱 실행 중 Client 내부 4040
Worker → Masterspark-master:7077Compose 내부 네트워크의 Master

포트 설정의 세 자리

127.0.0.1:8082:8081은 호스트 IP : 호스트 포트 : 컨테이너 포트 순서입니다.

  • 호스트 IP · 127.0.0.1: 같은 Windows PC에서 UI에 접속하도록 제한합니다.
  • 호스트 포트 · 8082: Windows 브라우저에서 Worker 2 UI를 열 때 쓰는 번호입니다.
  • 컨테이너 포트 · 8081: Worker 2 내부의 UI가 사용하는 번호입니다.

두 Worker는 서로 다른 컨테이너이므로 내부에서 각각 8081을 쓸 수 있습니다. Windows에서는 같은 IP의 같은 포트를 두 곳에 연결할 수 없어 8081과 8082로 나눕니다.

localhost는 “지금 실행 중인 곳 자신”
  • Windows 브라우저에서: localhost는 Windows PC입니다.
  • Worker 안에서: localhost는 그 Worker 컨테이너입니다.

그래서 Worker가 Master를 찾을 때는 localhost:7077 대신 spark-master:7077을 씁니다.

내부 연결은 서비스 이름으로

DNS(Domain Name System)는 이름을 IP 주소로 바꾸는 체계입니다. Compose 내부에서는 서비스 이름을 사용합니다.

  • 연결 순서: Worker가 spark-master의 IP를 조회한 뒤 그 IP의 7077로 연결합니다.
  • 이름을 쓰는 이유: 컨테이너 IP는 바뀔 수 있습니다. 숫자 IP를 코드에 고정하지 마세요.
  • DNS 구성: Docker가 제공하므로 별도 컨테이너는 필요 없습니다.

08

1부터 100까지 더하고 5050 확인하기

1부터 100까지 더하면 5050입니다. 정답을 미리 아는 문제로 Spark가 올바른 클러스터에서 실행됐는지 확인합니다.

학습용 비유 · 문제지를 나눠 풀고 합치기

숫자를 네 묶음으로 나눠 부분 합을 구하고 합치는 방식입니다. 아래는 학습용 모형이며, 실제 Spark의 Task와 집계 단계는 실행 계획에 따라 달라집니다.

코드 세 줄을 읽어 보세요

numbers = spark.range(1, 101, 1, 4)
total = numbers.selectExpr("sum(id) AS total").first()["total"]
assert total == 5050, f"Unexpected result: {total}"

입력: 1~100을 네 조각으로

  • 시작 · 1: 첫 숫자는 1입니다.
  • 끝 · 101: 끝값은 포함하지 않으므로 마지막 숫자는 100입니다.
  • 간격 · 1: 숫자가 1씩 증가합니다.
  • 입력 partition · 4: 데이터를 네 조각으로 나눕니다.

데이터를 표현하는 두 용어

  • partition(파티션): 데이터를 나누는 논리적 조각입니다.
  • DataFrame: 행과 열로 표현하는 데이터입니다. 여기서는 id 열에 숫자가 들어갑니다.

계산과 확인: 합계가 5050인지

  • selectExpr("sum(id) AS total"): id를 합산해 결과 열 이름을 total로 붙입니다.
  • first(): 결과의 첫 행을 가져옵니다.
  • ["total"]: 그 행에서 total 값을 꺼냅니다.
  • assert: 조건이 틀리면 오류를 내어 검증 실패를 드러냅니다.

손으로도 100 × 101 ÷ 2 = 5050인지 대조할 수 있습니다.

분할 수와 실행 자원은 다릅니다
  • 입력: partition 4개
  • 실행 자원: 총 Executor core 2개. 네 조각이 모두 동시에 처리되지는 않습니다.
  • 전체 Task 수: 집계 단계가 추가될 수 있어 4개로 단정할 수 없습니다.

run.sh가 정하는 실행 조건

제출 옵션과 목적
옵션이번 실행에서의 의미
--master spark://spark-master:7077로컬 모드 대신 Standalone Master에 자원을 요청합니다.
--deploy-mode client제출 명령이 실행되는 Client에 Driver를 둡니다.
Driver 512m / Executor 512m각 메모리 설정은 512 MiB입니다. 프로세스 전체 사용량과 같다고 단정하지 않습니다.
Executor 1 core / 총 2 cores두 Worker에서 Executor 하나씩 실행할 수 있도록 구성합니다.

run.sh 전체 원본 읽기

이 파일은 Linux의 Bash 스크립트입니다. PowerShell에 본문을 직접 붙여넣지 말고 아래의 docker compose exec … bash … 명령으로 실행합니다.

  • set -euo pipefail: 오류를 놓치지 않도록 하는 shell 옵션입니다.
  • "$@": 추가로 받은 인수를 Python 앱에 전달합니다.
#!/usr/bin/env bash
set -euo pipefail
exec /opt/spark/bin/spark-submit \
  --master spark://spark-master:7077 \
  --deploy-mode client \
  --driver-memory 512m \
  --executor-memory 512m \
  --executor-cores 1 \
  --total-executor-cores 2 \
  --conf spark.dynamicAllocation.enabled=false \
  --conf spark.driver.host=spark-client \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --conf spark.driver.port=39000 \
  --conf spark.blockManager.port=39001 \
  /opt/spark/apps/first_app.py "$@"
first_app.py 전체 원본 읽기
"""Week 2: submit, verify a known answer, observe the UI, and stop."""
import argparse
import time
from pyspark.sql import SparkSession

parser = argparse.ArgumentParser()
parser.add_argument("--wait-seconds", type=int, default=120)
args = parser.parse_args()

spark = SparkSession.builder.appName("Week02-First-App").getOrCreate()
try:
    spark.sparkContext.setLogLevel("WARN")
    print(f"MASTER={spark.sparkContext.master}", flush=True)
    print(f"APP_ID={spark.sparkContext.applicationId}", flush=True)
    assert spark.sparkContext.master == "spark://spark-master:7077"

    # Four input partitions. DataFrame syntax is covered next week.
    numbers = spark.range(1, 101, 1, 4)
    total = numbers.selectExpr("sum(id) AS total").first()["total"]
    print(f"SUM_1_TO_100={total}", flush=True)
    assert total == 5050, f"Unexpected result: {total}"
    print("CHECK=PASS", flush=True)
    print(f"UI observation: {max(0, args.wait_seconds)} seconds", flush=True)
    time.sleep(max(0, args.wait_seconds))
finally:
    spark.stop()
print("APP_STOPPED", flush=True)
  • argparse: 실행 인수를 읽습니다.
  • try: 계산을 수행하는 부분입니다.
  • finally: 정상 진행이나 Python 예외 시 정리를 시도하는 부분입니다.
  • time.sleep: 기본 120초 동안 UI를 볼 시간을 남깁니다.
  • spark.stop(): SparkSession을 종료합니다.

APP_ID=…도 출력되며 값은 실행마다 달라질 수 있습니다. 성공 여부는 아래 네 표시를 함께 확인하세요.

  • SUM_1_TO_100=5050: 합계가 정답과 일치합니다.
  • CHECK=PASS: 코드 안의 검증을 통과했습니다.
  • APP_STOPPED: 관찰 대기와 SparkSession 종료 후에 나오는 표시입니다.
  • 종료 코드 0: 실행 명령이 정상 종료됐습니다.

입력 partition이 4개라면 반드시 4개 core가 동시에 일하나요?

UI와 로그로 실행 상태 확인하기

계산 결과와 함께 로그·UI를 보면 앱이 어떻게 실행됐는지 확인할 수 있습니다.

  • 로그: 실행 중 일어난 일을 글로 기록한 자료입니다.
  • UI(User Interface): 상태를 화면으로 보여주는 인터페이스입니다.
학습용 비유 · 답안과 풀이 과정 함께 보기

정답과 풀이 과정을 함께 보듯, 코드의 검증 결과와 UI·로그를 함께 확인합니다.

Master UI · 자원과 앱

localhost:8080 열기

  • ALIVE Worker가 두 개 있는지
  • 관찰 대기 중 Running Applications에 앱이 있는지
  • 각 Worker에 Executor가 배정됐는지

Driver UI · 작업의 진행

localhost:4040 열기

  • Jobs: 실행 요청과 완료 상태를 확인합니다.
  • Stages: 작업을 나눈 처리 단계를 확인합니다.
  • Executors: Driver와 Executor 정보를 확인합니다.

합계 계산은 빠르게 끝날 수 있습니다. 120초 대기는 이미 완료된 작업과 앱 상태를 관찰할 시간입니다.

앱 종료 후 달라지는 상태
  • Driver·4040 UI: 관찰 대기가 끝나고 앱이 종료되면 함께 사라집니다.
  • Client 컨테이너: 앱 종료 후에도 계속 대기할 수 있습니다.

화면이 기대와 다르면 최근 로그부터

실행 위치: 같은 실습 폴더의 Windows PowerShell. 앱을 관찰 중이라면 두 번째 PowerShell을 열어 같은 폴더로 이동한 뒤 실행합니다.

docker compose logs --tail 80 spark-master spark-worker-1 spark-worker-2
  • --tail 80: 최근 로그 80줄을 확인합니다.
  • 찾을 내용: Master 시작, Worker·앱 등록, Executor 시작과 오류 메시지.

실시간 추적은 아래 명령을 사용합니다. Ctrl+C로 로그 추적을 끝냅니다.

docker compose logs -f spark-worker-1

10

컨테이너 중지·재시작·정리하기

앱을 종료해도 컨테이너는 남을 수 있습니다. 잠깐 쉬는지, 수업을 마치는지에 맞춰 환경의 수명을 관리합니다.

학습용 비유 · 일시 정지와 자리 정리

stop은 자리를 남긴 채 멈추기, start는 다시 시작하기, down은 자리 정리에 비유할 수 있습니다. 이미지와 호스트의 실습 파일은 남습니다.

종료 명령이 남기는 상태
명령컨테이너다음 행동
stop중지된 상태로 남음start로 같은 컨테이너 재시작
start기존의 중지된 컨테이너 실행Master 상태와 Worker 재등록 확인
down이 Compose 프로젝트의 컨테이너와 기본 네트워크 제거다음에는 사용할 네 서비스를 지정해 up -d로 다시 구성

잠깐 중지하고 다시 시작할 때

실행 위치: 실습 폴더의 Windows PowerShell. 앱이 정상 종료된 뒤 실행합니다.

docker compose stop
docker compose ps -a
docker compose start spark-master spark-worker-1 spark-worker-2 spark-client
docker compose ps -a
  • stop 후: 이번 실습에 사용한 네 컨테이너가 Exited 상태로 남습니다.
  • start 후: 지정한 네 서비스를 다시 시작합니다. Master healthy, Worker·Client Up, Master UI의 Worker 2개 재등록을 확인합니다.

실습을 끝낼 때

docker compose down
docker compose ps -a

확인: 이 프로젝트의 컨테이너 목록이 비어야 합니다. Spark 이미지와 Windows의 apps 파일은 다음 실습에서 재사용합니다.

다시 시작할 때는 클러스터 실행 단계로 돌아가 네 서비스를 지정한 명령을 사용하세요.

스스로 설명할 수 있으면 완료

  • 이미지 하나로 역할이 다른 컨테이너 네 개를 만들 수 있다.
  • Master는 자원을 배정하고, Worker는 Executor를 관리하며, Driver는 Task를 조정한다.
  • Windows의 localhost:8082는 Worker 2 내부 8081로 연결된다.
  • 로컬 이미지 검사, Worker 등록, 네트워크 검사, 계산 검증은 각각 다른 증거다.
  • 입력 partition 4개와 전체 Executor core 2개는 다른 개념이다.
  • 합계 5050, CHECK=PASS, APP_STOPPED와 종료 코드 0을 함께 확인한다.
  • stop과 down이 남기는 상태를 구분하고 다시 시작할 수 있다.
