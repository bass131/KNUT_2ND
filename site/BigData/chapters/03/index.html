01

큰 일을 나누면 무엇이 달라질까

분산처리는 큰 데이터를 나누어 여러 계산 자원이 함께 처리하는 방식입니다. 한 컴퓨터의 용량이나 처리 속도가 부족할 때 필요합니다.

학습용 비유 · 시험지 채점 나누기

시험지 네 묶음을 조교 두 명이 채점하면, 두 묶음은 처리하고 나머지는 기다립니다. 데이터 조각 수와 동시에 일할 자원 수는 다릅니다.

계산에 쓰는 자원

  • CPU / Core(코어): CPU는 명령을 실행하는 장치, 코어는 그 안에서 계산을 담당하는 단위.
  • 메모리: 계산 중 데이터를 보관하는 공간.
  • 디스크: 파일을 오래 저장하는 공간.

여러 컴퓨터의 자원을 쓰면 용량과 처리량을 늘리고, 실패한 작업 일부를 다시 실행하도록 설계할 수 있습니다.

자원을 늘리는 두 방법
방법실제 구조제약
Scale-up · 한 대 강화한 컴퓨터의 CPU와 메모리를 늘립니다. 실습에서는 기존 계산용 컨테이너의 자원 설정 증가에 대응합니다.장비 한 대가 지원하는 용량과 비용에 한계가 있습니다.
Scale-out · 대수 증가컴퓨터를 추가하고 작업을 나눕니다. 실습에서는 Worker 컨테이너 수를 늘려 구조를 관찰합니다.통신, 작업 배정, 결과 모으기와 장애 처리가 필요합니다.

데이터를 나누는 수와 일할 자원 수

Task(태스크)는 데이터 조각 하나를 처리하는 작업입니다. 이번 실습처럼 Task 하나가 코어 하나를 쓰면, 동시 실행 상한은 준비된 Task 수와 사용 가능한 코어 수 중 작은 값입니다.

  • 조각이 너무 적음: 일부 코어가 쉬게 됩니다.
  • 조각이 너무 많음: 작은 작업을 만들고 배정하는 비용이 커집니다.
  • 조각 크기가 불균형함: 가장 오래 걸리는 작업이 전체 완료를 늦춥니다.

나누고 모으는 데도 비용이 듭니다

  • Scheduling · 작업 배정: 어떤 자원에 어떤 작업을 맡길지 정하고 상태를 추적합니다.
  • Serialization / Deserialization · 직렬화와 역직렬화: 데이터를 전송할 바이트 형태로 바꾸고, 받은 쪽에서 복원합니다.
  • Network I/O · 네트워크 입출력: 프로세스나 컴퓨터 사이에서 데이터를 주고받습니다. 집계나 표 합치기에서는 데이터 재배치도 필요합니다.
한 PC 안의 여덟 Worker

모든 컨테이너는 같은 Windows PC의 CPU와 메모리를 공유합니다. 여러 물리 서버의 성능·장애 환경과는 다릅니다. 작은 데이터는 분산처리 준비 비용 때문에 단일 프로세스가 더 빠를 수도 있습니다.

02

계산을 맡는 엔진, Spark

Apache Spark는 작업 배정과 데이터 이동을 관리하며 분산 계산을 실행하는 처리 엔진입니다. 수업에서는 Python으로 Spark를 사용하는 PySpark를 씁니다.

학습용 비유 · 재료 창고와 조리실

파일 저장소가 재료를 보관하는 창고라면, Spark는 재료를 가공하는 조리실에 해당합니다. 저장과 계산의 역할을 구분하는 비유입니다.

Spark가 등장한 배경

Hadoop의 MapReduce는 모아 둔 데이터를 한 번에 처리하는 대규모 Batch(배치) 방식입니다. 반복 분석에서 데이터를 다시 읽고 중간 결과를 디스크에 쓰는 비용을 줄이려는 요구가 Spark의 배경이 되었습니다.

강의 연혁: 2009년 UC Berkeley AMPLab에서 시작 → 2010년 공개 → 2014년 Apache 최상위 프로젝트 승격.

계산을 계획하고 재사용하는 기능

  • DAG · 방향성 비순환 그래프: 처리 단계와 선후 관계를 화살표로 나타낸 실행 계획입니다. 연결을 따라가다 같은 단계로 되돌아오는 순환은 없습니다.
  • cache / persist · 재사용 데이터 유지: 반복해서 쓰는 데이터를 메모리나 디스크에 보관하는 기능입니다. 이번 배포 성능 코드는 이를 호출하지 않습니다.
  • Lineage · 계산 이력: 데이터 조각을 어떤 계산으로 만들었는지 기록합니다. 손실된 조각을 다시 계산하는 근거가 됩니다.
  • DataFrame / SQL: 열 이름이 있는 표 형태의 데이터와, 그 표를 조회·변환하는 방식입니다. 더 낮은 수준의 분산 데이터 인터페이스로 RDD도 있지만 이번 예제는 DataFrame을 사용합니다.

03

자원을 준비하는 역할과 계산하는 역할

컨테이너가 켜져 있어도 계산은 아직 시작되지 않았을 수 있습니다. 자원을 준비하는 역할과 제출한 프로그램을 계산하는 역할을 구분해 봅시다.

학습용 비유 · 강의실 배정과 수업 진행

시설 담당자는 강의실을 배정하고 수업 담당자는 수업을 진행합니다. 이처럼 Master는 자원을 배정하고 Driver는 계산 작업을 조정합니다.

실행 위치와 프로그램을 구분하기

  • Node(노드): 실행 위치. 이번 실습에서는 컨테이너로 구현합니다.
  • Process(프로세스): 실행 중인 프로그램. Worker와 Executor는 같은 컨테이너 안의 서로 다른 프로세스입니다.
  • Cluster(클러스터): 함께 일하는 계산 자원 구성.
  • Application(애플리케이션): 제출한 Spark 프로그램 하나.

위 그림은 학습용 구조 모형입니다. 다음 순서로 역할을 확인하세요.

  1. 준비: Master와 Worker가 켜지고 Client는 대기합니다.
  2. 제출: spark-submit이 Driver를 시작합니다.
  3. 자원 할당: 자원을 받은 Worker에서 Executor가 시작됩니다.
  4. 계산: Executor가 Driver에서 작업을 받고 결과를 보냅니다. Master가 모든 데이터를 중계하지는 않습니다.

Driver 안에서 사용하는 진입점

  • SparkSession: 표 형태의 데이터와 SQL을 사용하는 진입점.
  • SparkContext: 클러스터 연결과 실행을 조정하는 구성 요소.
  • --deploy-mode client: 배포 스크립트의 이 설정 때문에 Driver가 spark-client에서 실행됩니다.

04

DataFrame · 표가 합계 숫자가 되는 과정

여러 곳에 나뉜 데이터를 다루더라도, 코드에서는 열 이름으로 원하는 계산을 표현할 수 있어야 합니다. DataFrame(데이터프레임)은 이름이 있는 열로 구성된 표 형태의 분산 데이터입니다.

학습용 비유 · 나누어 보관한 성적표

성적표를 여러 조교에게 나누어 주어도 “점수 열의 합계”라는 요청은 같습니다. 표의 열과 실제 보관 묶음을 구분해서 생각해 보세요.

1. 행·열·스키마와 Partition 구분하기

  • Row(행): 데이터 한 건입니다. 숫자 예제에서는 숫자 하나가 한 행입니다.
  • Column(열): 각 행에서 같은 종류의 값을 담는 항목입니다. 예제의 열 이름은 id입니다.
  • Schema(스키마): 열 이름과 자료형 등 표의 구조입니다. id는 long, 즉 64비트 정수형입니다.
  • Partition(파티션): 분산 계산을 위해 행들을 나눈 조각입니다. 열이 하나여도 Partition은 여러 개일 수 있습니다.

Python 변수 numbers는 이 분산 표를 다루는 객체를 가리킵니다. 모든 행을 Python 리스트로 가져오는 것은 아닙니다. Spark는 데이터 생성과 변환 계획을 관리하고, 실행이 필요해지면 Executor가 조각별로 처리하게 합니다.

2. 실제 코드에서 입력 표 만들기

읽기용 Python 코드입니다. first_app.py에서 이미 만든 spark를 사용하며, PowerShell에 직접 입력하지 않습니다.

numbers = spark.range(1, 101, 1, 4)
  • 첫째 인자 1: 시작값을 포함합니다.
  • 둘째 인자 101: 끝 경계는 포함하지 않으므로 마지막 값은 100입니다.
  • 셋째 인자 1: 숫자가 증가하는 간격입니다.
  • 넷째 인자 4: 입력 Partition 수입니다. Worker 수나 열 수가 아닙니다.
입력 표의 논리적 모습 · 이해를 위한 일부 행, 실제 실행 출력 아님
행 설명id · long
시작값1
다음 값2
중간 행 생략3부터 99까지
마지막 값100

표는 100행 × 1열이고 입력 Partition은 4개입니다. 위 표는 숫자의 범위를 보여 주기 위한 배열입니다. 일반적인 DataFrame의 출력 순서는 명시적으로 정렬해야 보장할 수 있습니다.

3. 한 줄의 합계 코드를 네 단계로 풀기

배포 파일에는 다음 한 줄이 있습니다.

total = numbers.selectExpr("sum(id) AS total").first()["total"]

아래는 같은 계산을 설명용 변수로 나눈 코드입니다. 원본 파일을 이렇게 수정할 필요는 없습니다.

summary = numbers.selectExpr("sum(id) AS total")
row = summary.first()
total = row["total"]
assert total == 5050, f"Unexpected result: {total}"
  • selectExpr: SQL(표의 데이터를 조회·처리하는 언어) 식을 문자열로 받아 새 DataFrame을 정의합니다. 여기서는 전체 id 값을 더하는 계획입니다.
  • sum(id) AS total: sum은 합계, AS total은 결과 열의 이름입니다. 기존 numbers의 id 열을 덮어쓰지 않습니다.
  • summary.first(): 합계 표의 첫 행을 요구합니다. 이때 실제 계산이 필요해집니다. 입력의 첫 숫자 1을 가져오는 호출이 아닙니다.
  • row["total"]: 가져온 행에서 열 이름으로 값을 꺼냅니다. 이미 Driver가 받은 행을 읽으므로 별도의 분산 계산을 요청하지 않습니다.
  • assert: 참이어야 할 조건을 검사합니다. 합계가 5050과 다르면 오류를 내고 정상 확인 출력을 진행하지 않습니다.

05

계획을 만들고, 결과가 필요할 때 계산하기

Spark는 변환 계획을 모아 두었다가 결과가 필요할 때 계산합니다. 여러 처리 단계를 함께 보고 실행 방법을 정하기 위해서입니다.

학습용 비유 · 주문서를 모은 뒤 조리하기

주문서에 요리를 적는 단계와 실제로 조리하는 단계를 나누어 생각해 보세요. 변환은 계획을 만들고 실행 요청은 결과를 요구합니다. 주문서 줄 수가 실제 작업 수와 같지는 않습니다.

계획과 실행 요청

  • Transformation · 변환: 기존 DataFrame에서 새 DataFrame을 정의하는 연산입니다. 예제의 selectExpr("sum(id) AS total")은 합계를 구할 계획을 만듭니다.
  • Action · 실행 요청: 실제 결과가 필요해 계산을 시작시키는 연산입니다. 이번 예제의 first()가 이에 해당합니다.
  • Lazy Evaluation · 지연 실행: Action이 필요해질 때까지 변환을 모아 실행 계획으로 다루는 방식입니다.

  • 부분 합계: 325 + 950 + 1575 + 2200 = 5050.
  • 원본에서 완료한 Task: 입력 계산 4개 + 최종 집계 1개 = 총 5개.
  • 구분할 점: 입력 Partition이 4개여도 프로그램 전체의 Task가 4개인 것은 아닙니다.

학습용 비유 · 문장 카드를 잘라 단어별로 모으기

문장 카드를 단어마다 잘라 같은 단어끼리 쌓고, 더 두꺼운 묶음부터 놓는 과정입니다. 실제 Spark에서는 문자열을 나누고, 행을 늘리고, 그룹별로 집계한 뒤 정렬합니다.

1. 슬라이드의 전체 코드와 읽는 순서

원본을 읽는 예제

아래 HDFS(여러 컴퓨터에 파일을 나누어 저장하는 파일 시스템)의 week10 입력과 서비스는 이번 배포 자료에 없습니다. PowerShell 실행 명령이 아닙니다. 실제로 실행할 합계 실습은 뒤의 PPTX 실습·guide에서 진행합니다.

from pyspark.sql import SparkSession, functions as F
spark = SparkSession.builder.appName("df-wordcount").getOrCreate()
lines = spark.read.text("hdfs:///user/$USER/week10/input")
words = (lines
    .select(F.explode(F.split(F.col("value"), r"\s+")).alias("word"))
    .where(F.col("word") != ""))
result = words.groupBy("word").count().orderBy(F.desc("count"))
result.write.mode("overwrite").parquet("hdfs:///user/$USER/week10/df-output")
spark.stop()

functions as F는 Spark 함수들을 F라는 짧은 이름으로 쓰겠다는 뜻입니다. lines → words → result는 입력 표, 단어 표, 집계 표에 붙인 Python 변수 이름입니다.

3. col → split → explode → alias · 문장을 단어 행으로 바꾸기

words = (lines

    .where(F.col("word") != ""))

괄호가 많을 때는 가장 안쪽 함수부터 읽습니다. 다음 함수들이 만든 열 표현식을 select에 전달하면, 그 열을 가진 새 DataFrame을 정의합니다.

  • F.col("value"): 입력의 value 열을 가리키는 표현식입니다. 지금 당장 문자열 한 개를 꺼내는 동작은 아닙니다.
  • F.split(..., r"\s+"): 공백을 기준으로 문자열을 배열로 나눕니다. \s+는 하나 이상의 공백 문자를 뜻하는 정규식(문자열을 찾거나 나누는 규칙)이고, r은 Python에서 역슬래시를 그대로 쓰게 합니다.
  • F.explode(...): 배열의 원소 하나를 행 하나로 펼칩니다. 두 단어가 들어 있던 한 행이 두 행이 됩니다.
  • .alias("word"): 펼친 결과 열에 word라는 이름을 붙입니다.
  • .where(F.col("word") != ""): 단어가 빈 문자열이 아닌 행만 남깁니다. 비교 연산자 !=는 “같지 않다”라는 뜻입니다.

  • parquet(...): 열을 기준으로 데이터를 저장하는 Parquet(파케이) 형식으로 결과를 씁니다. 이 저장 요청이 계산을 요구하는 Action입니다. 출력 경로에는 여러 데이터 파일이 생길 수 있습니다.

6. 표의 변환이 Stage와 Shuffle로 연결되는 지점

  1. Stage A: 입력 조각에서 단어 분리, 빈 문자열 제거, 부분 집계를 수행합니다.
  2. 첫 Shuffle: 여러 조각에 있던 같은 단어의 집계 정보를 모읍니다. Stage B에서 단어별 최종 개수를 구합니다.
  3. 두 번째 Shuffle: 횟수 기준 전체 정렬에 맞게 데이터를 재배치합니다. Stage C에서 정렬하고 저장합니다.

이는 슬라이드가 설명하는 실행 구조입니다. 실제 Job·Stage 수는 Spark가 선택한 실행 계획에 따라 확인해야 합니다. 코드 한 줄이 반드시 Stage 하나에 대응하지는 않습니다.

학습용 비유 · 실험실 배치도와 실험 지시서

배치도는 사용할 장비를 준비하고, 지시서는 실험을 시작하며, 실험식은 계산을 정합니다. 설정 파일과 제출 스크립트, Python 코드도 역할이 나뉩니다.

1. compose.yaml · 계산을 시작할 환경 준비

  • compose.yaml: Master·Worker·Client 서비스와 네트워크를 정의합니다. 현재 파일에는 Worker 3개가 정의되어 있으며 이번 비교는 Worker 1·2만 사용합니다.
  • apps/run.sh: 준비된 환경에 Python 프로그램을 제출하고 Driver·Executor 자원 조건을 전달합니다.
  • apps/first_app.py: DataFrame을 만들고 합계를 검증한 뒤 UI 관찰 시간을 확보합니다.

docker compose up으로 컨테이너를 시작한 상태와 Application을 제출한 상태를 구분하세요. 계산 제출은 다음 명령으로 별도 수행합니다.

2. PowerShell 명령 · Client 안의 run.sh 호출

실행 흐름을 읽는 예시입니다. 실제 입력은 다음 PPTX 실습에서 준비를 마친 후 한 번 수행합니다.

docker compose exec spark-client bash /opt/spark/apps/run.sh --wait-seconds 300
  • docker compose exec spark-client: 이미 실행 중인 Client 컨테이너 안에서 명령을 실행합니다.
  • bash /opt/spark/apps/run.sh: 컨테이너 안의 Bash 셸로 제출 스크립트를 읽습니다. 호스트의 apps 폴더가 이 경로에 연결되어 있습니다.
  • --wait-seconds 300: 계산이 끝난 후 UI를 300초 유지하라는 Python 프로그램 인자입니다.

3. run.sh · spark-submit으로 Driver 시작

배포 파일의 전체 코드입니다. Bash 스크립트를 읽기 위한 것으로, 아래 내용을 PowerShell에 붙여 넣지는 않습니다.

#!/usr/bin/env bash
set -euo pipefail
exec /opt/spark/bin/spark-submit \
  --master spark://spark-master:7077 \
  --deploy-mode client \
  --driver-memory 512m \
  --executor-memory 512m \
  --executor-cores 1 \
  --total-executor-cores 2 \
  --conf spark.dynamicAllocation.enabled=false \
  --conf spark.driver.host=spark-client \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --conf spark.driver.port=39000 \
  --conf spark.blockManager.port=39001 \
  /opt/spark/apps/first_app.py "$@"
  • set -euo pipefail: 명령 실패나 미정의 변수 같은 오류를 놓치지 않도록 셸 동작을 설정합니다.
  • exec와 spark-submit: 셸 프로세스를 Spark 제출 프로그램으로 교체합니다. 이 예제는 client 모드이므로 Driver가 Client 컨테이너에서 실행됩니다.
  • 줄 끝의 \: 여러 줄에 쓴 내용을 하나의 Bash 명령으로 이어 줍니다.
  • 마지막 "$@": 전달받은 인자를 유지합니다. 앞의 --wait-seconds 300이 first_app.py까지 도착합니다.

"""Week 2: submit, verify a known answer, observe the UI, and stop."""
import argparse
import time
from pyspark.sql import SparkSession

parser = argparse.ArgumentParser()
parser.add_argument("--wait-seconds", type=int, default=120)
args = parser.parse_args()

spark = SparkSession.builder.appName("Week02-First-App").getOrCreate()
try:
    spark.sparkContext.setLogLevel("WARN")
    print(f"MASTER={spark.sparkContext.master}", flush=True)
    print(f"APP_ID={spark.sparkContext.applicationId}", flush=True)
    assert spark.sparkContext.master == "spark://spark-master:7077"

    # Four input partitions. DataFrame syntax is covered next week.
    numbers = spark.range(1, 101, 1, 4)
    total = numbers.selectExpr("sum(id) AS total").first()["total"]
    print(f"SUM_1_TO_100={total}", flush=True)
    assert total == 5050, f"Unexpected result: {total}"
    print("CHECK=PASS", flush=True)
    print(f"UI observation: {max(0, args.wait_seconds)} seconds", flush=True)
    time.sleep(max(0, args.wait_seconds))
finally:
    spark.stop()
print("APP_STOPPED", flush=True)

6. 인자 읽기와 SparkSession 생성

  • argparse: 명령 뒤에 준 인자를 읽는 Python 도구입니다. type=int는 정수로 읽고, default=120은 생략했을 때의 값입니다.
  • parse_args(): 전달받은 300을 args.wait_seconds에 저장합니다. 인자 이름의 하이픈은 속성 이름에서 밑줄이 됩니다.
  • SparkSession.builder: 세션 설정을 준비합니다. appName은 UI에 보일 이름이고, getOrCreate()는 기존 세션을 사용하거나 새 세션을 만듭니다.
  • spark.sparkContext: 현재 연결과 Application 정보를 확인합니다. 실제 계산을 조정하는 SparkContext는 Driver 안에서 동작합니다.

7. 연결 확인 → DataFrame 계산 → 정답 검증

  • setLogLevel("WARN"): 이후 로그 출력을 경고 이상 중심으로 줄입니다. 앞서 나온 시작 로그까지 없애지는 않습니다.
  • MASTER와 APP_ID: 연결 주소와 실행 식별자를 출력합니다. 첫 assert는 의도한 분산 Master에 연결했는지 검사합니다.
  • numbers와 total: 앞서 본 표 → 합계 표 → Row → 정수의 흐름입니다. first()에서 결과 계산을 요구합니다.
  • SUM_1_TO_100와 두 번째 assert: 숫자를 출력하고, 손계산한 정답 5050과 비교합니다. 통과한 뒤에야 CHECK=PASS가 출력됩니다.
  • flush=True: 관찰할 메시지가 출력 버퍼에 머물지 않도록 즉시 내보냅니다.

8. UI 대기 → 자원 정리 → 다음 실습

  • max(0, args.wait_seconds): 음수 대기 시간을 0으로 보정합니다.
  • time.sleep(...): 합계 계산이 끝난 후 Python 프로그램을 잠시 유지합니다. 이 시간에 UI를 봅니다.
  • finally: spark.stop(): try 블록의 성공·실패와 관계없이 Spark 종료를 시도합니다. Session과 Context를 종료하고 Executor를 정리합니다.
  • APP_STOPPED: 정상 경로에서 종료 정리를 마친 뒤 출력합니다. 앞서 예외가 발생하면 finally가 실행되어도 이 출력에 도달하지 않을 수 있으므로 오류 로그도 확인합니다.

프로그램이 끝나도 Master와 Worker 컨테이너는 다음 제출을 기다릴 수 있습니다. 뒤의 실습에서 Application 종료와 클러스터 종료를 따로 관찰합니다.

준비 4 · 제출 옵션이 Python 코드로 이어지는 경로

다음은 실제 run_performance.sh에서 가져온 전체 제출 명령입니다. 읽기용 Bash 코드이며 PowerShell에 직접 붙여 넣지 않습니다. 다음 절의 docker compose exec 명령이 이 파일을 컨테이너 안에서 실행합니다.

#!/usr/bin/env bash
set -euo pipefail

TOTAL_EXECUTOR_CORES="${TOTAL_EXECUTOR_CORES:-1}"

exec /opt/spark/bin/spark-submit \
  --master spark://spark-master:7077 \
  --deploy-mode client \
  --driver-memory 512m \
  --executor-memory 512m \
  --executor-cores 1 \
  --total-executor-cores "${TOTAL_EXECUTOR_CORES}" \
  --conf spark.dynamicAllocation.enabled=false \
  --conf spark.driver.host=spark-client \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --conf spark.driver.port=39000 \
  --conf spark.blockManager.port=39001 \
  /opt/spark/apps/performance_app.py "$@"
  • TOTAL_EXECUTOR_CORES: PowerShell 명령의 -e TOTAL_EXECUTOR_CORES=4가 이 실행 프로세스에 환경변수 4를 전달합니다. 스크립트는 그 값을 --total-executor-cores에 넣습니다. 생략하면 1입니다.
  • --executor-cores 1: Executor 하나가 사용할 코어를 1개로 고정합니다. Worker 하나도 1 Core이므로 전체 코어 상한을 늘리면 여러 Worker에 Executor를 배정할 수 있습니다.
  • spark.dynamicAllocation.enabled=false: 이번 비교에서는 동적 자원 할당을 끄고 제출한 코어 조건을 유지합니다.
  • "$@": 명령 뒤의 --end, --partitions, --repetitions, --wait-seconds 인자를 Python 파일로 그대로 전달합니다. 코어 수는 제출 옵션이고 입력 범위·반복 수는 Python 프로그램의 인자입니다.

준비 5 · performance_app.py의 실제 계산 과정 읽기

아래는 performance_app.py 원본의 핵심 발췌입니다. 읽기용 Python 코드이며 앞의 SparkSession 생성과 인자 검사는 생략했습니다. 변수 args에는 명령행 인자를 읽은 값이, spark에는 생성한 SparkSession이 들어 있습니다.

numbers = spark.range(1, args.end, 1, args.partitions)
expected = (args.end - 1) * args.end // 2
elapsed_values = []

for run_number in range(1, args.repetitions + 1):
    started = time.perf_counter()
    total = numbers.selectExpr("SUM(id) AS total").first()["total"]
    elapsed = time.perf_counter() - started

    assert total == expected, f"Unexpected result: {total}"
    elapsed_values.append(elapsed)
    print(f"RUN_{run_number}_SECONDS={elapsed:.3f}", flush=True)

median_seconds = statistics.median(elapsed_values)
print(f"SUM_RESULT={total}", flush=True)
print(f"MEDIAN_SECONDS={median_seconds:.3f}", flush=True)
print("CHECK=PASS", flush=True)
print(f"UI observation: {max(0, args.wait_seconds)} seconds", flush=True)
time.sleep(max(0, args.wait_seconds))
  • 1. 입력 DataFrame: spark.range는 id 열을 가진 분산 DataFrame을 만듭니다. 기본값에서는 1부터 10억까지의 행을 128개 Partition으로 다룰 계획입니다. Python 리스트나 10억 행 파일을 먼저 만들지 않습니다.
  • 2. 예상 정답: expected는 Python 정수입니다. 1부터 end - 1까지의 등차수열 합 공식을 계산하며 Spark 실행과 독립적으로 정답을 확인하는 기준입니다.
  • 3. 반복과 타이머: range(1, args.repetitions + 1)은 기본값에서 1, 2, 3 순으로 반복합니다. started와 elapsed는 시간을 나타내는 Python 실수이며 elapsed의 단위는 초입니다. 반복마다 집계 표현식을 새로 만들고 결과를 요청합니다.
  • 4. 반환형 변화: selectExpr(...)는 total 열이 있는 집계 DataFrame을 정의합니다. first()가 계산을 요청해 첫 Row를 Driver로 가져오고, ["total"]이 그 행에서 Python 정수 합계를 꺼냅니다. 기본 예상값은 500000000500000000입니다.
  • 5. 검증 후 기록: assert가 예상 합계와 일치하는지 검사한 다음 시간을 elapsed_values라는 Python 리스트에 저장합니다. 정답이 다르면 검증 오류로 중단하므로 성공한 측정처럼 기록하면 안 됩니다.
  • 6. 대표값과 대기: statistics.median은 세 시간 중 가운데 값을 돌려줍니다. RUN_1_SECONDS부터 RUN_3_SECONDS, 합계, 중앙값, PASS를 출력한 뒤 UI 관찰 시간만큼 기다립니다. 관찰 대기는 위 타이머 밖이므로 중앙값에 더해지지 않습니다.

원본은 이후 finally에서 spark.stop()을 호출하고 APP_STOPPED를 출력합니다. 하나의 Application 안에서 같은 입력 정의로 세 번 집계하지만 cache()나 persist()는 호출하지 않습니다.

다음 절로 이동할 조건: 표 A의 네 조건과 실제 2 / 2 Executor 수를 기록했습니다. Worker는 8개를 유지하고, 마지막 실행의 APP_STOPPED 이후 전체 코어 상한만 2로 바꿉니다.

exercise · Worker가 많아도 덜 쓸 수 있다

Worker는 여덟 개 유지하고 전체 Executor 코어 상한만 두 개로 줄입니다. 준비된 자원과 Application이 쓰는 자원을 비교합니다.

학습용 비유 · 열린 창구와 실제 담당 창구

창구 여덟 개 중 두 곳에만 업무를 배정하면 나머지는 그 업무를 처리하지 않습니다. 이번 설정도 Executor마다 1 Core이므로 전체 2 Core 상한이 참여 수를 제한합니다.

조건 B · Worker 8개 유지·전체 코어만 2개 · exercise 7단계

실행 위치: 3장 실습 폴더의 PowerShell. Worker 8개가 등록되어 있고 이전 Application이 종료된 상태에서 실행합니다.

docker compose exec -e TOTAL_EXECUTOR_CORES=2 spark-client bash /opt/spark/apps/run_performance.sh --end 1000000001 --partitions 128 --repetitions 3 --wait-seconds 0

확인 B · 준비한 코어와 실제 할당 구분하기

  • Master의 Total Cores: 8.
  • 이 Application의 Used Cores: 최대 2.
  • Executor: 다른 Application이 없고 등록·할당이 정상이면 2개. Driver 행은 제외합니다.

학습용 모형은 자원 사용과 입력 Task의 동시 실행 상한을 보여 줍니다. 속도 예측은 아니며 최종 집계·통신 시간은 별도로 필요합니다.

exercise · 측정값을 구조로 설명하기

시간이 줄었다는 결론에는 같은 정답, 같은 입력, 실제 자원 사용이라는 근거가 필요합니다. 마지막으로 여덟 Core 실행을 관찰하고 비교 결과를 설명합니다.

학습용 비유 · 사람이 늘어도 좁은 작업장은 같다

사람이 늘어도 통로와 작업대를 공유하면 기다림이 생깁니다. 이 실습도 한 PC의 CPU·메모리를 공유하므로 Worker 수만큼 빨라진다고 보장할 수 없습니다.

UI observation: 300 seconds가 나오면 확인하세요.

  • Master · localhost:18080: ALIVE Worker 8개 / Used Cores 8.
  • Driver · localhost:24040의 Executors: Driver를 제외한 Executor 8개.
  • Jobs / Stages: 각 반복의 Task 수와 완료 상태. guide의 총 5 Task를 이 실험에 그대로 대입하지 않습니다.

결과 해석 · 표 A와 표 B로 답하기 · exercise 9단계

  • 정확성: 모든 조건에서 같은 SUM_RESULT와 CHECK=PASS가 나왔는지 먼저 확인합니다. 정답이 다르면 속도 비교를 결론 내리지 않습니다.
  • 동시 실행의 증가: Worker와 코어를 함께 늘리면 동시에 실행할 입력 Task가 늘어날 수 있습니다. 입력 Partition 수는 128로 같습니다.
  • 비용과 자원 경합: Executor 관리, Task 배정, 결과 집계, 컨테이너 간 통신에 시간이 필요합니다. 같은 PC의 자원을 놓고 경쟁하면 8 Worker가 4 Worker보다 느리거나 비슷할 수 있습니다.
  • 첫 실행의 영향: JVM 초기화와 실행 코드 생성의 영향을 받을 수 있습니다. 중앙값은 유난히 큰 한 측정값의 영향을 줄여 주지만 모든 변동을 제거하지는 않습니다.
  • 2 / 2와 8 / 2 비교: Application이 사용하는 코어 상한은 같습니다. Worker를 더 만들었다는 사실만으로 네 배 빨라질 이유는 없으며, 실제 차이는 측정값과 자원 상태를 근거로 설명합니다.
